## 结论（先看这段，⚠️ 描述的是**修复前**的状态）

**1. 主因不是模型大小，也不是后端，是 `parseNumbered()` 把模型完全正确的输出判成了失败。**

24 句真实课堂转写、4 个 6 句批次，模型（1.5B，贪心解码）**每一批都输出了完美对齐的 6 行**。
但生产版 `parseNumbered()` 只认下来 1 批：

| 解析器 | 对齐成功率 |
|---|---|
| 生产版 `parseNumbered()` | **1 / 4** |
| 只去掉「编号行正文过 `META_STRICT_RE`」这一条，其余不动 | **4 / 4** |

3 次误判的原因完全相同：`cleanTranslation()` 最后一行

```js
if (META_STRICT_RE.test(t)) return '';        // 修复前的 translate-llm.js:438
// 现在已经是： if (!numbered && META_STRICT_RE.test(t)) return '';   // 第 478 行
```

把**以「好的，」开头的合法译文整条删成空字符串**。
空译文 → `collectNumbered()` 的 `if (!val) continue` → 该编号缺号 → `got.size !== n` → 返回 `null`
→ 判定「批量对齐失败」→ 触发整条重试/拆批降级链。

被误杀的真实译文（模型输出的第 4 行）：

```
1|最高法院裁定第一修正案保护这种言论。
2|我们不会读那篇文章，除非它很长，但这会引出关于隐私变化和数字时代对隐私理解的变化的问题。
3|你的作业是问题集四，下周五之前交。
4|好的，下一周的阅读材料是隐私和技术章节。      ← 这一行被当成「好的，以下是翻译：」删掉了
5|这引发了政府是否可以迫使披露这些信息的问题。
6|还有什么问题吗，在我们继续到下一个案例之前？
```

这不是偶发。`META_STRICT_RE` 会吃掉的合法课堂译文：

| 译文 | 对应原文 | 结果 |
|---|---|---|
| 好的，我们开始上课 | okay so let's get started | ❌ 删空 |
| 好的，下一周的阅读材料是… | okay so the reading for next week is… | ❌ 删空 |
| 好的，让我们看看各巡回法庭怎么分裂的 | okay so lets look at how the circuits have split | ❌ 删空 |
| 当然，这也是考点 | sure, and that's on the exam too | ❌ 删空 |
| 以上是本周的重点 | so that's the main takeaway this week | ❌ 删空 |
| 下面是三个要件 | so there are three elements | ❌ 删空 |

`okay so` / `alright` / `well` / `sure` 是美国课堂口语**最高频的句首词**，ASR 几乎每隔几句就出一次。
本文 24 句语料里有 4 句这样开头，它们分布在 3 个不同批次里 —— 所以 4 批错 3 批。
更讽刺的是：`translate-llm.js` 自己的 few-shot 示例就是 `okay so the court said…` → `好，法院说…`，
是在**主动教模型**用「好…」开头，然后再用正则把它删掉。

**2.（修复前）对齐失败会把 1 次 generate 放大到最多 10 次。这是「6 句跑不完」的直接原因。**
修复后同一组形态实测是 1~7 次，见下表右列。

`_translateChunk()` 的降级链是「同批重试(贪心) → 对半拆 → 递归 → 逐句」。用假 llm 注入真实的
模型输出形态，统计一次 6 句批处理（`batchSize=6`，`mtllm-client.js` 里写死的值）的 generate 次数：

| 模型输出形态 | 修复前 | **现在（已落地，实测）** |
|---|---|---|
| 完美编号输出 | 1 | **1** |
| 开头有「好的，以下是翻译：」（真客套话） | 1 | **1** |
| **完全对齐，但一条译文以「好的，」开头** | **4** | **1** ✅ |
| 被 `max_new_tokens`/超时截断 | 10 | **4** |
| 多吐了第 n+1 条 | 10 | **1** ✅ |
| 两句合并成一行 | 10 | **2** |
| 后半段丢了 `\|` 分隔符 | 10 | **5** |
| 完全没有编号 | 10 | **7**（= 逐句，最坏情况的上界） |
| 其中一条复读劣化（只需重翻那一条） | 2 | **2** |

右列是 2026-09-21 复核时 `node web/js/mtllm-bench.mjs --sim` 实跑的结果，
和建议 ② 表格里预测的「打捞式」列**逐格相符**。

真实模型接进生产版 `translateMany()` 端到端跑 6 句，`batchSize=6`：

```
n=6 temp=0.2 cap=838  生成 92tok  8.6s     ← 对不齐，白跑
n=6 temp=0   cap=838  生成 94tok  9.1s     ← 对不齐，白跑
n=3 temp=0.2 cap=504  生成 49tok  6.4s
n=3 temp=0.2 cap=366  生成 35tok  7.4s
合计 4 次 generate，31.5s / 6 句 = 5.25 s/句
```

而同样 6 句、同样模型、**一次就对齐**时只要 8.2s = **1.36 s/句**。
→ 修复前的代码在**一个批次上白白烧掉了 17.7 秒（56% 的时间）**，跑的是两次注定被丢弃的完整生成。
（①②③ 落地后这条链路已经不存在：第一次贪心 + 打捞，同一批只需 1 次 generate。）

**3. 两份实测数据的矛盾就此解开。**

| 观察 | 真实解释 |
|---|---|
| node / 0.5B / q8 / bs=4 → 2.2 s/句 | 没有（或很少）触发对齐失败，接近理想速度 |
| 浏览器 / 1.5B / WebGPU → >20 s/句 | 1.36~2 s/句的理想速度 × 4~10 倍放大 |

本文实测：**1.5B q4f16 在 node CPU 上是 1.36 s/句，比那台 0.5B q8 的 2.2 s/句还快。**
所以「模型大小」和「后端」都不是主因 —— **放大才是**。

**4. Worker 批量超时这个坑，主协调者已经在改了（复核于 2026-09-21 09:3x）。**

```js
// web/js/mtllm-client.js 当前值：已经是 7200000（2 小时）
const r = await this._call({ type: 'many', items, batchSize: 6 }, 7200000, '批量翻译', …);
```

原先是 3600000（60 分钟）：按浏览器观察到的 >20 s/句，300 句要 ~100 分钟，会撞上硬超时
→ `_call` reject → `translateMany()` 返回 `[]`，整节课的重译全部丢失（`onEach` 已推给界面的那部分除外）。
现在 2 小时的上限，在修好放大之后（预计 7~18 分钟）有足够余量。
仍然建议：**一次 `many` 调用不要吞掉整节课**，按 30~50 句一段分多次调用，
这样超时只会牺牲一段而不是整篇，也天然有了断点续传。

## 可落地的提速建议（按收益排序）

### ① ✅ **已落地** — 修 `cleanTranslation()`：编号行的正文不要过 `META_STRICT_RE`

**收益：对齐成功率 1/4 → 4/4，端到端 5.25 s/句 → 1.4 s/句，快 3.8 倍。改一行。**

`META_STRICT_RE` 的本意是丢掉模型在**整段输出开头**写的「好的，以下是翻译：」。
但 `1|好的，下一周的阅读材料是…` 这一行**已经带了编号**，它在结构上就不可能是客套话 ——
模型不会给客套话编号。判断应该放在「这一行有没有编号」上，而不是放在正文内容上。

- 批量路径（`collectNumbered`）：编号行的正文**只做去引号/去重复编号**，不做客套话判断。
- 单句路径（`parseSingle`）：那里没有编号可依赖，保留现有逻辑；但建议把
  `好的[，,、]` / `以上是` / `下面是` 从 `META_STRICT_RE` 挪走，只在**整段输出的第一行且后面还有更多行**时才丢。
  「好的，我们开始上课」作为唯一一行输出时必须保留。

### ② ✅ **已落地** — 对齐失败时改用「打捞式降级」，不要推翻整批

现在只要少一个编号就把**整批作废**，重试 + 递归对半拆。
改成：解析时**拿到几条算几条**，只对缺号的那几条单独重翻。

| 模型输出形态 | 修复前 | 打捞式（**现已落地，数字为实测**） | 省掉 |
|---|---|---|---|
| 完全对齐但被误杀一行 | 4 | **1**（1 批 + 0 单句） | 75% |
| 多吐了第 n+1 条 | 10 | **1** | 90% |
| 两句合并成一行 | 10 | **2**（1 批 + 1 单句） | 80% |
| 被截断（只出了 3/6 条） | 10 | **4**（1 批 + 3 单句） | 60% |
| 后半段丢分隔符（只出了 2/6 条） | 10 | **5** | 50% |
| 完全没有编号 | 10 | **7**（等于逐句） | 30% |

关键性质：**最坏情况退化成逐句（n+1 次），永远不会超过它**。修复前的递归拆分会超过。
复核实跑已确认这张表逐格成立（`--sim` 表 A 右列）。

另外 `sawStray` 那条建议放宽：当 `1..n` **全部到齐**、多出来的编号**都 > n** 时，
说明模型只是在末尾续写了一条客套话，不是错位，可以直接采纳 `1..n`（上表第 2 行，10 次 → 1 次）。
只有出现 **< 1 或与 1..n 冲突**的编号时才算真错位。

### ③ ✅ **已落地** — 第一次就用贪心解码（`do_sample=false`），别先采样再重试

现在 `_translateChunk()` 第一次用 `temperature=0.2`，失败了才用贪心。
实测两者对齐率和速度都一样（18 句各 1/3、25.1s vs 24.1s），但采样**引入了不确定性**：
同一批输入两次跑可能一次对齐一次不对齐（本文 `bs=6` 那次端到端跑里就出现过）。
翻译是确定性任务，直接贪心 —— 少一次重试就少 2.8~9 秒。
`repetition_penalty: 1.08` 可以保留，实测没有压掉 `|` 分隔符。

### ④ `max_new_tokens`：现在给得太松，但它**不是**当前的速度瓶颈 —— 且收紧有一个真实的坑

> 🔧 **本节第一版有一处方法错误，已修正。** 第一版用 `生成 tok >= cap - 2` 判「被截断」，
> 这在「译文正好用掉 94 token」时是个假阳性：`cap=96` 被误报成已截断，而它的输出和
> **不设限那一档一字不差**。修正后的判据是「撞上限 **且** 输出文本与不设限那一档不同」，
> 真实截断阈值是 **88，不是 96**。`mtllm-bench.mjs` 的表 D 已经按这个判据重写并重跑。

模型正常会自己吐 EOS，所以上限放松并不会变慢（复核实跑，6 句 551 字符）：

| `max_new_tokens` | 实际生成 tok | 耗时 s | 对齐 | 与不设限输出一致 | 被截断 |
|---|---|---|---|---|---|
| 838（生产公式） | 94 | 8.3 | ✅ | 是 | 否 |
| 256 | 94 | 8.3 | ✅ | 是 | 否 |
| 160 | 94 | 8.3 | ✅ | 是 | 否 |
| 120 | 94 | 8.3 | ✅ | 是 | 否 |
| 96 | 94 | 8.4 | ✅ | 是 | **否**（第一版误报成「是」） |
| **88** | 88 | 8.1 | **✅** | 否 | **是** ⚠️ |
| 80 | 80 | 7.6 | ❌ | 否 | 是 ⚠️ |
| 72 | 72 | 7.2 | ❌ | 否 | 是 ⚠️ |
| 64 | 64 | 6.8 | ❌ | 否 | 是 ⚠️ |

生产公式（`英文字符 × 1.2 + 24n + 32`）给 838，实际只用掉 **11%**。
实测标定：**生成 token ≈ 英文字符 × 0.17**（n=1/3/5/6/8 实测比值 0.154 / 0.150 / 0.151 / 0.171 / 0.176）。

**⚠️ `cap=88` 这一行是本节最重要的发现，比省时间重要得多：**
输出被砍在 `6|还有什么问题吗，在我们`，**半句话**，但六个编号一个不少，
`parseNumbered()` 判定 ✅ 通过，打捞式降级也不会触发 —— **静默截断**，
界面直接拿到一条被腰斩的译文。整个模块的安全承诺是「最坏是慢，不是错位」，
而截断恰好绕开了编号这道唯一的自证机制（编号能证明**条数**对，不能证明**每条都写完了**）。

所以收紧 `max_new_tokens` 不是纯赚：它把「跑飞时慢」换成了「余量不够时无声地丢字」。

建议：
- 公式改成 **`英文字符 × 0.30 + 16n + 24`**（6 句给 ~285 token，是实测 94 token 的 3 倍余量）。
  它不会让正常情况变快，但把**模型跑飞时的最坏单次耗时**从 838 token（≈52s，会撞 45s 软超时）
  压到 285 token（≈18s）。
- **下限是 0.30 倍，不要再往下压。** 实测 88 token（≈0.16 倍）就开始截断，
  而 96（≈0.17 倍）是安全的 —— 安全边界只有一格之差，没有任何余量可让。
- **配套加一道截断守卫**（这条比改公式更值）：`_runBatch()` 已经拿得到生成的 token 数，
  当「生成 token 数 ≥ `max_new_tokens` - 2」时，不要相信这次的 `parseNumbered` 结果，
  按对齐失败处理走打捞/逐句。没有这道守卫，公式收得越紧，静默截断的概率越高。

### ⑤ `batchSize`：对齐已修好，可以用 **6~8**（`mtllm-client.js` 现在传 6，合理）

每次 generate 的成本 = 固定成本 + 解码。实测线性拟合：

```
固定成本（~550 prompt token 的 prefill + 开销） ≈ 2.8 ~ 3.0 s   ← 与 batchSize 无关
解码速率 ≈ 16 ~ 18 tok/s
```

固定成本是常数，所以批越大每句越便宜：

| batchSize | 每批 s | 每句 s | 300 句（无放大） |
|---|---|---|---|
| 1 | 3.8 | 3.77 | 18.8 min |
| 3 | 5.7 | 1.91 | 9.6 min |
| 5 | 7.7 | 1.54 | 7.7 min |
| 6 | 8.7 | 1.45 | 7.2 min |
| 8 | 10.7 | 1.33 | 6.7 min |
| 12 | 14.6 | 1.22 | 6.1 min |

8 往上收益已经很小（8→12 只快 8%），而对齐风险随 n 上升。**6~8 是最佳点。**
⚠️ 这条警告在 ①② 落地后已经解除（原文是「①② 不改就必须降到 3」）。
修复后复核实跑的放大率：bs=3 → 3.0x、bs=6 → 4.0x（修复前 4.0x / 10.0x），
绝对值降下来了，但**随 batchSize 单调上升的趋势还在** —— 所以别超过 8。
另外 `translate-llm.js` 的 `DEFAULT_BATCH = 5`、`MAX_BATCH = 8`，
`mtllm-client.js` 显式传 `batchSize: 6`，三者一致，不用动。

### ⑥ 分隔格式：**保留编号，不要改成纯换行**

| 格式 | 对齐 | 每句 s | 生成 tok |
|---|---|---|---|
| 编号 `k\|`（修复前的解析器） | 1/4 | 1.37 | 192 |
| 编号 `k\|`（**现行**解析器） | **4/4** | 1.37 | 192 |
| 纯换行 | 3/3 | **1.18** | **156**（少 19%） |

纯换行确实更快（少生成序号和分隔符的 token），实测也没掉链子。
**但仍然不建议换**：编号是唯一能**自证对齐**的手段。纯换行时模型把两句合并成一行，
行数正好还对得上的话（比如同时把另一句拆成两行），会产生**静默错位** ——
这正是 `translate-llm.js` 注释里说「错位比翻错严重得多」要防的那件事。
19% 的 token 换掉整个安全属性不划算。修好 ① 之后编号版已经 4/4，没有换的必要。

### ⑦ few-shot 要留着

| 配置 | prompt tok/批 | 对齐 | 18 句耗时 |
|---|---|---|---|
| 贪心 + few-shot | 542 | 1/3 | 25.1s |
| 贪心 + **无** few-shot | 431 | **0/3** | 23.5s |

去掉 few-shot 只省 6% 时间，但对齐率归零（模型完全不按编号输出）。留着。

## 时间预估（300 句 ≈ 90 分钟的课）

### 实测基准（node CPU / Apple 芯片 / 1.5B q4f16）

| 环节 | 实测 | 300 句 |
|---|---|---|
| opus-mt 一路（`Xenova/opus-mt-en-zh` q8） | ≤ 0.30 s/句 | ≤ 1.5 min |
| LLM 一路，修好后，bs=6，贪心 | 1.36 ~ 1.43 s/句 | 7.0 ~ 7.2 min |
| LLM 一路，**修复前**的代码，bs=6 | 5.25 s/句 | **26 min** |（已不适用）
| 逐句取优融合（确定性规则，不调模型） | — | < 1 s |

> opus-mt 那个 0.30 s/句是我用裸 pipeline 调的，**没有**带 `mt.js` 自己的生成参数
> （它跑飞时会一直吐「。。。。」到上限）。`mt.js` 有 `max_new_tokens` 约束，只会**更快**。
> 所以 0.30 s/句是一个**上界**，可以放心当保守值用。

### 给用户看的数字（保守）

**修好 ①②③ 之后，一节 90 分钟的课（约 300 句）双模型重译，预计 15 分钟左右，最坏 25 分钟。**

这个数字是这么来的：

```
LLM 一路（bs=6，修好对齐）              7.2 min   ← 实测
+ 真正的对齐失败残留（按 1/8 批次算）     +0.6 min   ← 估算
+ 逐条劣化守卫触发的单句重翻（按 5% 算）  +1.8 min   ← 估算
+ opus-mt 一路                          +1.5 min   ← 实测上界
+ 模型载入 / WebGPU shader 编译          +0.5 min   ← 估算（浏览器首次尤其慢）
─────────────────────────────────────────────────
node CPU 小计                          ≈ 11.6 min
× 浏览器 WebGPU 折算系数 1.0 ~ 1.5       ≈ 12 ~ 18 min
```

**⚠️ 必须诚实说明的不确定性**：本次调查**没有测浏览器 WebGPU**（浏览器面板被占用）。
上面的「折算系数 1.0~1.5」是估算。理由是 transformers.js 在 Apple 芯片上跑 1.5B q4f16 时，
WebGPU 与 onnxruntime-node CPU 的解码速率通常在同一量级，而浏览器侧还要和录音/ASR 抢资源。
**所以对用户报 15 分钟、并明确说"可能到 25 分钟"，不要报 7 分钟。**
想要准数，需要在浏览器里跑一次 `bs=6` 单批，量出每句秒数再乘 300。

### 不修的话

**（历史存档，①②③ 落地前的数字）现在的代码：300 句需要 40 ~ 100 分钟**（node CPU 实测 5.25 s/句 × 300 = 26 分钟，
浏览器上还要再乘一个系数）。Worker 超时已经放宽到 2 小时，不会再整体 reject，
但让用户等 40~100 分钟这一档仍然不能交付。

### 如果 15 分钟还嫌久

- 换 `onnx-community/Qwen2.5-0.5B-Instruct`（权重已和「AI 笔记」共用，但 `web/models/`
  下**目前只有 1.5B**，需要先下载）。参数量小 3 倍，预计 **5 ~ 7 分钟**，代价是质量回退到
  任务描述里记的那一档（First Amendment → 「宪法」）。**未实测。**
- 只对「opus-mt 和 LLM 分歧大」的句子跑 LLM。课堂里短句（`right`、`okay`、`any questions`）
  opus-mt 本来就够用，能省掉 30~40% 的句子。这是融合策略层面的优化，属于主协调者的范围。
- 让重译在关闭 session 后**后台跑**，做好进度条和断点续传 —— 用户不需要盯着看。
  这比压缩时间更实际。

## 独立复核（2026-09-21，第二、第三次跑，每次换一次进程）

结论 1、2 都用**新跑的数据**验过。⚠️ 第三次复核是在 ①②③ 落地**之后**跑的，
所以 `--sim` / 表 C 量到的是修复后的行为（见文首「落地状态」），速度类数字不受影响、可比：

```
node web/js/mtllm-bench.mjs --sim
  # 第二次（修复前）：truncated/stray/merged/lost_sep/freeform = 10x，okay_so = 4x
  # 第三次（修复后）：4x / 1x / 2x / 5x / 7x，okay_so = 1x —— 正是建议 ② 预测的那一列
node web/js/mtllm-bench.mjs --real --n 12 --batch 3,6 --lib <transformers.node.mjs>
```

| 指标 | 第一次 | 复核 |
|---|---|---|
| 1.5B q4f16 / node CPU，6 句一批 | 8.6 s，94 tok | 7.6 ~ 8.0 s，94 tok |
| 纯生成每句 | 1.36 s | **1.30 s** |
| 生产 `parseNumbered` 对齐率 | 1/4 | **1/2**（同一批被同一行「好的，」误杀） |
| 去掉编号行的客套话过滤后 | 4/4 | **2/2** |
| 拟合固定成本 / 解码速率 | 2.8~3.0 s / 16~18 tok/s | 2.87 s / 19.7 tok/s |
| max_new_tokens 96 开始截断 | 是 | 是 |

另外**不加载模型**也能单独证明结论 1（任何人 10 秒可复现）：

```js
import { parseNumbered } from './translate-llm.js';
parseNumbered('1|最高法院裁定…\n2|…\n3|…\n4|好的，下一周的阅读材料是…\n5|…\n6|…', 6)
// -> null   ← 六行全对，只因为第 4 行以「好的，」开头
```

`好的，…` / `当然，…` / `以上是…` / `下面是…` 开头的合法译文都会被删空 → 整批判失败；
`注意：…` 开头的不会（它只在 `META_TRAILING_RE` 里）。

## 仍然未实测的部分（不要当成结论用）

1. **浏览器 / WebGPU 一次都没测过**（按要求没碰浏览器面板）。所有真实数字都是
   node + onnxruntime-node CPU。「折算系数 1.0~1.5」是估算。给用户报数字时用保守档。
2. **0.5B 那一档的「5~7 分钟」纯属估算** —— `web/models/` 下只有 1.5B 的权重。
3. **对齐率样本很小**（每轮 2~4 个批次）。方向确定（误杀是结构性的），
   但「4 批错 3 批」的具体比例取决于语料里有多少句以 okay so / alright / well / sure 开头。
4. **`max_new_tokens` 的 0.30 倍系数是按本语料标定的**（生成 token ≈ 英文字符 × 0.15~0.18）。
   换模型或遇到大段连读的长句时余量会变薄，**不要往下压**，并且请配套加截断守卫（见 ④）。
